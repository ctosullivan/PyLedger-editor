# UAT Checklist — 1.1.0 Round 4 (expanded smart dates)

**Branch:** `release/1.1.0`
**Covers:** the expanded smart-date vocabulary in the `Ctrl+O` filter popup's
Date From / Date To fields — see `CHANGELOG.md [Unreleased]` for the full
write-up. New keywords: `this week`, `last week`, `this month`, `this year`,
a year-month shorthand (`2026-02`, or unpadded `2026-2`), and a month name
with or without a year (`september`, `sep 2026`, `September 2026`).

Also covers the investigation into the round-3 report "transaction added
from filter was not saved as expected" — **no code defect was found**; see
the note at the end of this checklist.

**Not re-covered here** (already signed off in rounds 1–3, unaffected by
this round's changes): basic filtering, empty-filter no-op, Clear button
field-reset, footer visibility, main-editor and filter-popup autocomplete,
the transaction count on the status bar, `last month`/`ytd`/`q1`-`q4`
bounding, and the `Ctrl+O`/`Ctrl+L` combine behavior. See
[`1.1.0-round3-checklist.md`](1.1.0-round3-checklist.md) if you want to
re-run those.

**Prerequisite:** [`SETUP.md`](SETUP.md) — `git pull` first.

## 1 — Deterministic keywords (don't depend on today's date)

These give the same result regardless of when you run this checklist —
prefer these if you want a clean pass/fail without doing date arithmetic.

- [ ] `Ctrl+O`, **Date from** = `2024-02`, leave **Date to** blank, Apply.
  - **Expected:** all 20 `Filler transaction *` entries, and only those —
    **20/26**. (`2024-02` alone is bounded to the whole of February 2024,
    same as `2026-02` was in round 3's tests.)
- [ ] Clear. **Date from** = `2024-2` (unpadded month), Apply.
  - **Expected:** identical result to `2024-02` above — **20/26**.
- [ ] Clear. **Date from** = `august 2026`, Apply.
  - **Expected:** `Landlord` and `Employer` only — **2/26**.
- [ ] Clear. **Date from** = `Aug 2026` (abbreviation, mixed case), Apply.
  - **Expected:** identical result — **2/26**.
- [ ] Clear. **Date from** = `september 2026`, Apply.
  - **Expected:** `Opening balances` only — **1/26** (confirms the
    unpadded `2026-9-1` in the source parses correctly against a
    zero-padded query).
- [ ] Clear. **Date from** = `smarch 2026` (not a real month), Apply.
  - **Expected:** rejected with a notification (invalid date), same as
    any other unparseable string — view unchanged.
- [ ] Clear before moving on.

## 2 — Relative-to-today keywords (`this week`, `last week`, `this month`, `this year`)

These depend on the actual date you're running this on, since they're
relative to today. Work out what today's month is before you start:

- [ ] `Ctrl+O`, **Date from** = `this month`, Apply.
  - **Expected:** if you're testing in **September 2026**, this matches
    `Opening balances` only (**1/26**). If you're testing at some other
    time, it should match whatever September-2026-or-later content
    happens to fall in the current real month — most likely **0/26** —
    which is correct, just confirm no error and no crash.
- [ ] Clear. **Date from** = `last month`, Apply.
  - **Expected:** if testing in **October 2026**, this matches
    `Opening balances` (**1/26**). If testing in **September 2026**
    (i.e. the same month as `2026-9-1`), `last month` means August 2026,
    so this matches `Landlord` + `Employer` (**2/26**). Otherwise, most
    likely **0/26** — confirm no error either way.
- [ ] Clear. **Date from** = `this week`, Apply.
  - **Expected:** the fixture has no content reliably inside "this
    week" for most testing dates — **0/26** is the likely, and
    acceptable, result. Just confirm the filter applies cleanly (no
    error, no crash) and the status bar correctly reads
    **"View: Filtered (Ctrl+O) (0/26)"** rather than silently doing
    nothing.
- [ ] Clear. **Date from** = `last week`, Apply.
  - **Expected:** same as above — most likely **0/26**, occasionally
    **1/26** if `2026-9-1` happens to fall in "last week" relative to
    today. Either is correct; just confirm it applies without error.
- [ ] Clear. **Date from** = `this year`, Apply.
  - **Expected:** if testing anytime in 2026, matches `Opening
    balances`, `Landlord`, and `Employer` — **3/26**. (2024-dated
    entries are excluded.)
- [ ] Clear before moving on.

## 3 — Auto-fill bounding still applies to the new keywords

- [ ] `Ctrl+O`, **Date from** = `this month`, **Date to** left blank,
      Apply, note the count. Then, without clearing **Date from**, set
      **Date to** explicitly to something far in the future, e.g.
      `2030-01-01`, and re-Apply.
  - **Expected:** the count with **Date to** blank should be the *same*
    as with **Date from** = `this month` alone in round 1's section
    above — i.e. `this month` used alone is bounded to just that month,
    not "from the 1st of this month onward forever." Widening **Date
    to** to `2030-01-01` should pull in *more* rows (anything from the
    start of the month onward, not just within it) if there's any later
    content — with this fixture there may not be, which is fine, the
    point is the two counts aren't required to match once you've
    overridden the auto-fill.
- [ ] Clear before moving on.

## Note: round-3 "transaction not saved" report

This was investigated by reproducing the exact reported scenario four
different ways against the actual application, including a full
Ctrl+O-filter → add-transaction → Ctrl+S flow through the real UI. In
every case the new transaction was correctly present in the saved file —
**no code defect was found**. The likely cause of the confusing result
was round 3's checklist itself, which told testers to expect the
*visible* count to go "from 6 to 7" after two `Ctrl+L` presses — but each
`Ctrl+L` press also changes which cleared-state is required (it's ANDed
with the still-active date filter), so the visible set's composition
changes at each step rather than simply gaining one row. That wording has
been corrected in `1.1.0-round3-checklist.md`, and two permanent
regression tests were added
(`tests/test_filter_popup.py::TestFilterPopupEditPersistence`) to guard
against this ever silently breaking in the future.

- [ ] If you have time, re-run round 3's §1 persistence step (now
      corrected to recommend `Ctrl+S` directly rather than `Ctrl+L`
      cycling) to confirm for yourself that the save is reliable.
